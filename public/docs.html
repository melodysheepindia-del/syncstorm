Documentation

SyncStorm gives any web page rooms, shared state, live cursors, and presence in roughly 10 lines of plain JavaScript — no build step, no dependencies.

Installation

Drop one <script> tag into your page:

<!-- Self-hosted (recommended) -->
<script src="/syncstorm.js"></script>

<!-- Or directly from your deployed URL -->
<script src="https://your-app.railway.app/syncstorm.js"></script>

No npm, no bundler, no TypeScript required. The library is a single 300-line file that uses the browser's built-in WebSocket.

Quick start (~10 lines)

// 1. Join a room (creates it if it doesn't exist)
const room = SyncStorm.join('my-room', { name: 'Alice' });

// 2. React to shared state changes
room.onState(state => {
  document.getElementById('votes').textContent = state.votes;
});

// 3. React to who's in the room (including cursor positions)
room.onPresence(users => console.log('online:', users.map(u => u.name)));

// 4. React to connection status
room.onStatus(s => console.log(s)); // 'connected' | 'reconnecting' | 'disconnected'

// 5. Write shared state
room.set('votes', 42);

// 6. Send live cursor position
document.addEventListener('mousemove', e => room.sendCursor(e.clientX, e.clientY));

// 7. Leave when done
room.leave();

API Reference

SyncStorm.join(roomId, options) method

Connects to the server, creates the room if it doesn't exist, and returns a Room object. Auto-reconnect starts immediately.

ParameterTypeDescription
roomIdstringNon-empty room identifier. Use crypto-random IDs for privacy (e.g. crypto.randomUUID()).
options.namestringDisplay name shown to other participants. Truncated to 32 chars. Default: 'Anonymous'.

room.set(key, value) method

Write a key into shared state. value can be any JSON-serialisable type. While offline, the write is queued and replayed after reconnect. Returns the room (chainable).

ConstraintLimit
Key length128 characters
Value size8 KB (serialised JSON)
Message size16 KB total

room.onState(callback) event

Fires whenever shared state changes. Receives a shallow copy of the full room state object. Also fires immediately if state already exists. Returns the room (chainable).

room.onState(state => {
  // state is a plain object: { key: value, ... }
  console.log(state.score); // e.g. 42
});

room.onPresence(callback) event

Fires when the participant list changes or when any participant moves their cursor. Receives an array of user objects. Returns the room (chainable).

room.onPresence(users => {
  // users: Array<{ id: string, name: string, cursor: {x,y} | null }>
  for (const u of users) {
    console.log(u.name, u.cursor); // cursor is null until they move
  }
});

room.onStatus(callback) event

Fires whenever the connection state changes. Also fires immediately with the current status. Returns the room (chainable).

room.onStatus(status => {
  // status: 'connected' | 'reconnecting' | 'disconnected'
});

room.sendCursor(x, y) method

Broadcast your pointer position to other participants. Automatically throttled to ~20 fps (50 ms). Safe to call on every mousemove event. Has no effect while offline. Returns the room (chainable).

room.disconnect() method

Drops the current WebSocket connection. The library auto-reconnects with exponential backoff. Queued offline writes survive and are replayed on reconnect. Useful for testing or simulating network drops.

room.leave() method

Permanently closes the connection and discards the pending queue. No further reconnect attempts are made. Call when the user navigates away.

State consistency

How it works

The server is the single source of truth. Each key stores { value, rev } where rev is a strictly-increasing integer assigned by the server in the order messages arrive.

Conflict policy — per-key Last-Write-Wins

When two clients write the same key concurrently, the server applies both in arrival order and increments rev each time. The second write wins — there is no merge or three-way diff. All clients then converge to the same final value because the server broadcasts the update to everyone.

Example: Alice writes x = "alice" and Bob writes x = "bob" at the same millisecond. If Bob's message reaches the server first, the final state is x = "alice" (Alice's write arrived second). Both clients see the same update sequence.

Snapshot on (re)connect

On every connect or reconnect, the server sends a full snapshot message containing every key in the room. The client replaces its local state with this snapshot — stale local values never overwrite newer server data.

Offline queue

Writes made while offline are stored in a per-key queue. After the snapshot arrives, queued writes are re-sent to the server in order. The server applies them with the same LWW rule. This means:

  • Your offline edits are not silently lost.
  • If another peer wrote the same key while you were offline and their write has a higher rev, your queued write will overwrite it when it arrives (LWW in arrival order).
  • This is intentional — the last client to reconnect wins for any contested key.

Automatic reconnect

The library reconnects automatically with exponential backoff:

AttemptDelay
1st retry1 second
2nd retry2 seconds
3rd retry4 seconds
4th retry8 seconds
5th+ retry10 seconds (cap)

On successful reconnect: backoff resets to 1 s, snapshot is applied, offline queue is replayed.

Live cursors

Call room.sendCursor(x, y) on every mousemove event. The library throttles sends to ~20 per second. Other participants receive cursor data via onPresence — each user object has a cursor field that is null until they move and { x, y } after that. Cursors are removed from the presence list when a user disconnects.

document.addEventListener('mousemove', e => {
  room.sendCursor(e.clientX, e.clientY);
});

room.onPresence(users => {
  for (const u of users) {
    if (u.cursor) moveCursorEl(u.id, u.cursor.x, u.cursor.y);
  }
});

Known limitations

No persistence. Rooms live in server memory only. A server restart deletes all rooms and state. Do not use SyncStorm for data that must survive beyond a session.
  • No authentication. Anyone who knows a room ID can join it. Use unguessable crypto-random IDs to limit access.
  • No history / event log. Late joiners get the current state snapshot only, not a replay of past writes.
  • No fine-grained CRDT. Concurrent edits to the same key always resolve with LWW — the last write to arrive at the server wins.
  • Single-process server. State is in a Node.js Map. Horizontal scaling requires an external state store (Redis pub/sub, etc.) which is out of scope for this version.
  • Cursor positions are viewport-relative. They make sense only when all clients see an identical layout.
